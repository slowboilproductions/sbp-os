## What the motion layer is now (the architecture — read before touching it)
**One island drives all of it:** `site/src/components/Motion.astro`, included once in `BaseLayout`. It is reduced-motion-gated in exactly ONE place, so pages stay declarative (data-attributes only). The gate:
- An **inline `<head>` boot-script** (`BaseLayout.astro`) adds `html.motion` to `<html>` **only when JS is on AND `prefers-reduced-motion` is not `reduce`**, before first paint (no FOUC). 1800ms **watchdog** force-reveals everything if the island never boots.
- **All initial-hidden CSS sits behind `html.motion`** (`global.css`). So **no-JS and reduced-motion render fully static and fully visible** — verified by the auditor.
- The `<html>` element persists across Astro View Transitions, so the class survives client nav; the island re-inits on `astro:after-swap`. Per-element `*Wired` flags prevent listener leaks.

**The data-attribute vocabulary (how to extend without breaking the gate):**
- `[data-reveal]` — generic scroll reveal (optional `--ri` index for stagger delay).
- `[data-anim="hero"]` — hero block whose direct children rise in sequence.
- `[data-anim="stagger"]` + `[data-anim-item]` — grid that populates its items (StackGrid).
- `[data-zpush]` — z-axis push (Operational Dashboard signature). **Put it on a WRAPPER, never on an element that also runs a JS tilt** (transform fight).
- `[data-drift]` + `[data-drift-layer][data-rate="…"]` — parallax (Marketing signature); offset clamped ±130px.
- `.rec[data-reveal]` with per-row `--ri`/`--rd` — CRM staggered-rows pattern.
- `.btn--primary` → magnetic; `.card` → cursor glow — both auto-wired, fine-pointer only.
- Hero **boot-up count-up** lives in `DashboardPanel.astro`'s own script (self-contained), NOT the island.
